Drag a card over the bin and it settles into place, or pull it back out and
it springs back to its original size. Let go while it's over the bin and
the card disappears, and the rest of the list quietly closes the gap on its
own, the way a browser naturally reflows content rather than something
explicitly animating it shut.

## What's happening

Drag a card toward the bin and it shrinks and slides as it gets close, like
it's being pulled in. Drop it inside and it's gone, and the rest of the list
quietly closes up the space it left. Pull it back out before letting go, and
it snaps back to its normal size, like nothing happened.

## How it's built

[`useDraggable`](/composables/use-draggable) moves the card, and
[`useAnimatable`](/composables/use-animatable) handles everything else:
shrinking the card as it enters the bin's hit area, restoring it if it
leaves, and playing the bin or spring-back reaction on release. The list
closing its gap isn't animated at all. Collapsing the binned card's
placeholder is enough for the browser's own layout engine to reflow the rest
of the list.

Nothing is positioned by hand. Each card sits inside a ghost element that
holds its place in normal document flow, and the card itself is absolutely
positioned within that ghost, so dragging the card never disturbs the layout
around it. Binning a card collapses its ghost, and the list closes the gap
because the browser reflows it, not because anything measured or moved it.

The card is also split in two. A fixed-size handle is what `useDraggable`
moves. The visible card inside that handle is what changes shape. Keeping
those separate means the drag and the resize never fight over the same
`transform` property.

Crossing into the bin is treated as a state, not a gradient. `onUpdate`
tests the handle's centre point against the bin's bounding box and reports a
boolean. `useAnimatable` eases a single `0 → 1` value from that boolean, and
the card's width, height, and offset are all interpolated from that one
number, so the "inside the bin" look isn't three animations. It's one value
driving three properties.

::note
Geometry is measured once in `onGrab` rather than on every frame. Nothing in
the list moves until the card is released, so a per-frame
`getBoundingClientRect()` would buy nothing and cost a layout on every tick.
::

## Building it yourself

1. Wrap each item in a ghost element that stays in normal document flow. This is what preserves list position and lets the list reflow when a card is removed.
2. Inside the ghost, split the card into a fixed-size handle and a visible card absolutely positioned within it. `useDraggable` moves only the handle.
3. Call `useDraggable(handle, { onGrab, onUpdate, onRelease })`. In `onGrab`, measure the ghost's rest rect and the bin's rect once with `getBoundingClientRect()`, and precompute the size delta between them.
4. In `onUpdate`, test whether the handle's centre point falls inside the bin's rect, and report that boolean only when it changes.
5. Drive a [`useAnimatable`](/composables/use-animatable) value from that boolean, from 0 to 1, and interpolate the card's width, height, and offset from it in a computed style.
6. On release: if the boolean was true, mark the item as binned and collapse its ghost's height to close the gap. If false, ease the animatable value back to 0 and reset the draggable.
