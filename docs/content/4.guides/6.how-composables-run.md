The nine composables share the same rules for building, rebuilding and
tearing down their AnimeJS instance. This page covers those rules once.
Each [composable page](/composables/introduction) covers its own API.

## Where you can call a composable

Call a composable in `setup()` unless you have a reason not to. The badges
on each page and the table on the
[composables index](/composables/introduction) say where else it works and
what it accepts before mount.

### Instant play

Composables marked Instant play also work outside `setup()`, for example in
a click handler. There they build the animation on the next tick and read
`parameters` once, so later `ref` changes are ignored. Outside `setup()`
there is no component to read from, so three more things differ:

- `app.config.ts` defaults, [`provideAnimeDefaults()`](/guides/configuration#scope-defaults-to-part-of-the-app) and presets do not apply.
- `reducedMotion` is not honored, so the animation always plays.
- Nothing reverts the animation. Call `revert()` yourself, or each call stacks another animation on the same targets.

To keep reactivity, call the composable in `setup()` and call `play()` on
the returned object from the handler. `useAnimate` autoplays on mount, so
set `autoplay: false` when the handler starts the animation:

```ts
const animation = useAnimate('.box', { opacity: [0, 1], autoplay: false })

button.addEventListener('click', () => animation.play())
```

A top-level `await` in `<script setup>` still counts as `setup()`.

`useAnimate`, `useWaapiAnimate` and `useScrambleText` return an empty
placeholder until the component mounts, so a method called during
`setup()` does nothing. `useAnimatable` has no setters until then, so
calling one throws.

### Buffered

Composables marked Buffered build their instance after mount. Chainable
methods, the ones that return the instance, can be called before then.
`nanime` queues them and replays them in order once the instance exists.
A method that is not queued is `undefined` until then, so calling it throws
a `TypeError`.

`useAnimeTimeline` called outside `setup()` builds its instance on the next
tick and queues chained calls until then.

These calls are queued before mount:

| Composable | Queued before mount |
| :--- | :--- |
| `useAnimeTimeline` | `add`, `set`, `remove`, `call`, `label`, `sync`, `stretch`, `refresh`, `revert` and the playback methods `play`, `pause`, `resume`, `restart`, `reset`, `reverse`, `alternate`, `seek`, `cancel`, `complete`, `init`, `resetTime` |
| `useDraggable` | `disable`, `enable`, `reset`, `revert`, `stop`, `setX`, `setY`, `scrollInView`, `animateInView` |
| `useAnimeScroll` | `link`, `refresh`, `revert` |
| `useAnimeLayout` | `record` |

## When does an animation rebuild?

Composables run on the client only. Called in `setup()`, these rebuild when
a `ref`, getter or reactive object they receive changes: `useAnimate`,
`useWaapiAnimate`, `useScrambleText`, `useAnimeTimeline`, `useAnimeLayout`
and `useSplitText`. A rebuild reverts the old instance first and then builds
a new one. It restarts the animation unless
[`keepTime`](/guides/configuration#set-module-options) is on, which only
`useAnimate`, `useScrambleText` and `useAnimeTimeline` take.

Three composables work differently:

- `useAnimatable` rebuilds only when `target` changes. Its options are read once.
- `useDraggable` rebuilds when `target`, `trigger` or `container` changes. A `ref` in the listed options updates it in place.
- `useAnimeScroll` takes a plain or `reactive()` object, not a `ref` or getter.

Callbacks are usually left out of the comparison that decides a rebuild.
`useAnimate`, `useAnimeTimeline` and `useAnimeLayout` skip the shared AnimeJS
callbacks. `useWaapiAnimate` skips only `onComplete`. `useScrambleText`
skips them in `animationOptions` but not in `scrambleOptions`.
`useSplitText` skips none, so a getter that returns a new inline function
counts as a change each time it runs. `useAnimatable` never compares its
options at all.

The running instance keeps the callback it was built with. Read changing
values through a `ref` inside the callback.

## What defaults and reduced motion apply

Defaults for a composable come from `nanime.composables` in `app.config.ts`,
the nearest
[`provideAnimeDefaults()`](/guides/configuration#scope-defaults-to-part-of-the-app)
call, or the active [preset](/guides/presets).

| Setting | Read by |
| :--- | :--- |
| `nanime.composables.animate` and the preset's `animate` entry | `useAnimate` |
| `nanime.composables.draggable` and the preset's `draggable` entry | `useDraggable` |
| `keepTime` | `useAnimate`, `useScrambleText`, `useAnimeTimeline` |
| `reducedMotion` | `useAnimate`, `useWaapiAnimate`, `useAnimatable`, `useScrambleText`, `useAnimeTimeline`, `useAnimeLayout` |

`useWaapiAnimate`, `useAnimatable`, `useSplitText` and `useAnimeScroll` read
no composable defaults. [Configuration](/guides/configuration#how-a-default-is-picked)
covers the order defaults are picked in, and
[Accessibility](/guides/accessibility) covers the reduced motion setting.

Under `reducedMotion`, animations jump to their end state. `useAnimatable`
sets every numeric option to `0` and the easing to `linear`,
`useScrambleText` completes at once, and `useAnimeLayout` only measures the
initial layout and does not animate.

A key passed as `undefined` still replaces the default, so leave the key out
instead.

## Read properties after mount

Applies to the buffered composables. `useAnimeTimeline`, `useDraggable` and
`useAnimeScroll` build their instance on the tick after the component
mounts. Until then property reads give `undefined`, and a method that is
not queued is `undefined` too.

```ts
const draggable = useDraggable('.card')

onMounted(async () => {
  await nextTick()
  console.log(draggable.x)
})
```

Read properties after `await nextTick()` inside `onMounted`, or inside a
callback such as `onDrag`. `useAnimeLayout` builds during mount, so its
members are ready inside `onMounted`.

## Caveats that apply across composables

### Do not destructure the returned instance

Applies to `useAnimate`, `useWaapiAnimate`, `useAnimatable` and
`useScrambleText`.

```ts
// wrong: play() throws when called
const { play } = useAnimate('.target', { opacity: 0 })

// right
const animation = useAnimate('.target', { opacity: 0 })
animation.play()
```

The returned object gives back methods without their instance, so a
destructured `play()` runs with no `this` and throws. A destructured
property such as `progress` is a copy of the value at that moment. A
destructured `useAnimatable` setter such as `x` carries its own instance and
works until `target` changes, then keeps driving the old animatable. Keep
the returned object and call methods on it.

### Properties do not update templates

Applies to every composable that returns an AnimeJS instance. `useSplitText`
returns real refs and `useAnimatable` returns setters, so it does not apply
to them.

```ts
// wrong: progress never updates inside a template interpolation
// <p>{{ animation.progress }}</p>

// right: update a ref inside onUpdate
const progress = ref(0)
const animation = useAnimate('.target', {
  opacity: [0, 1],
  onUpdate: self => progress.value = self.progress,
})
```

Interpolating properties like `progress` in a template displays only their
initial value. AnimeJS updates them outside Vue's reactivity tracking, so
nothing triggers a re-render. Assign the current value to a `ref` inside the
`onUpdate` callback. `useWaapiAnimate` has no `onUpdate`, so use
[`useAnimate`](/composables/use-animate) when a template needs live
progress.

### Plain object targets must be reactive

Applies to `useAnimate` and `useAnimatable`.

```ts
// AnimeJS writes to a plain object directly, so Vue never sees the change
const position = { x: 0, y: 0 }
useAnimate(position, { x: 100 })

// reactive(), shallowReactive() and ref() make the object reactive
const tracked = reactive({ x: 0, y: 0 })
useAnimate(tracked, { x: 100 })
```

AnimeJS writes to the properties of the object it receives. Vue only sees
those writes when the object is reactive. A `shallowRef` holding an object
is not.
